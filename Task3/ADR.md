## <a name="_u8xz25hbrgql"></a>**Нефункциональные требования**

| № | Требование |
|---|---|
| 1 | Доступность сервисов — 99,9% времени; при сбое в ЦОД должен работать резервный ЦОД. |
| 2 | Время отклика на все операции — в пределах миллисекунд. |

| 4 | АБС может масштабироваться только вертикально из‑за БД. |

| 6 | Защита чувствительных данных шифрованием трафика (HTTPS/TLS). |

## <a name="_qmphm5d6rvi3"></a>**Решение**

### Диаграммы C4 (ссылки на локальные файлы)

- [Контекстная диаграмма](C4_Context.puml)
- [Диаграмма контейнеров](C4_Container.puml)

### Основные компоненты и интеграции (по диаграммам)

**Контекстный уровень (C4 Context):**
- **Внешние участники:** клиенты (новые/действующие), оператор кол‑центра, сотрудник бэк‑офиса.
- **Системы:** Сайт, Интернет‑банк, Кол‑центр, АБС, СМС‑сервис, Телеком‑оператор.
- **Ключевые потоки:**
  - Сайт → Кол‑центр: передача заявок.
  - Интернет‑банк → промежуточный слой → АБС: подача заявок без прямого вызова АБС.
  - АБС → СМС‑сервис → Телеком‑оператор: уведомления.

**Уровень контейнеров (C4 Container) — детализация:**
- **АБС:** `АБС Application` (Delphi, PL/SQL) + `АБС Database` (Oracle).
- **Интернет‑банк:** `IB Web` (ASP.NET MVC) + `IB DB` (MS SQL) + новый `Rate & Limit Cache Service` (Go).
- **Кол‑центр:** `CC API` (Java Spring Boot) + `CC DB` (PostgreSQL).
- **СМС‑сервис:** оркестрация уведомлений + очередь.
- **Промежуточная очередь заявок:** RabbitMQ/Kafka для буферизации и контроля темпа нагрузки на АБС.

### Логика принятых решений и выбор технологий

- **Rate & Limit Cache Service на Go:** быстрый ответ (мс), кэширование ставок, фоновая синхронизация с АБС (Read‑only). Учитывая опыт с Go — логично реализовать на Go и деплоить в Kubernetes с HPA.
- **Изоляция АБС:** интернет‑банк не вызывает АБС напрямую; заявки идут через очередь, чтобы не создавать пиковые нагрузки.
- **Кэширование справочников:** решает проблему загрузки данных >1 секунды.
- **Горизонтальное масштабирование:** интернет‑банк и новые сервисы (Rate Cache, очередь) масштабируются горизонтально; АБС — только вертикально.
- **Использование Kafka (перспективно):** для асинхронных процессов (СМС, уведомления, статусы). Для MVP можно начать с RabbitMQ, позже перейти на Kafka.
- **Защита данных:** HTTPS/TLS на всех внешних каналах; минимизация хранения чувствительных данных.
- **Документация и контракты:** OpenAPI для Rate Cache и промежуточных API, AsyncAPI для событий (СМС, статусы заявок).

## <a name="_bjrr7veeh80c"></a>**Альтернативы**

1. **Прямая интеграция интернет‑банка с АБС (без промежуточного слоя).**  
   Плюсы: меньше компонентов, проще внедрить.  
   Минусы: высокий риск перегрузки АБС, нарушение требований надёжности и производительности.
2. **Хранение ставок только в XLS без переноса в систему.**  
   Плюсы: минимальные доработки.  
   Минусы: риск ошибок, потери версий, невозможность автоматизации, нарушение требований поддерживаемости.
3. **Реализация всего MVP на новых технологиях (например, полностью новые микросервисы).**  
   Плюсы: современный стек, гибкость.  
   Минусы: отсутствие экспертизы в банке, высокие риски внедрения и поддержки, нарушение ограничений по использованию существующих технологий.
4. **Отказ от СМС‑подтверждения в MVP.**  
   Плюсы: упрощение реализации.  
   Минусы: снижение безопасности, несоответствие стандартам финансовых операций.

## Недостатки, ограничения, риски

- **Ограничение масштабируемости АБС:** АБС может масштабироваться только вертикально, что ограничивает возможности по обработке пиковых нагрузок. Решение — минимизировать прямые вызовы АБС и использовать асинхронные процессы.
- **Риск перегрузки АБС при росте заявок:** даже при асинхронной подаче заявок АБС остаётся узким местом. Решение — контроль темпа обработки, приоритизация заявок, мониторинг нагрузки.
- **Зависимость от экспертизы команд:** новые сервисы (на Go, Kafka) требуют наличия специалистов в банке. Решение — постепенное внедрение, обучение, документирование.
- **Переход от XLS к системе:** миграция данных и процессов может занять время и потребовать ручного труда. Решение — планировать миграцию как отдельный этап, автоматизировать проверку данных.
- **Сложность переключения ЦОД:** автоматическое переключение требует дополнительных настроек и тестирования. Решение — разработать чёткий план аварийного восстановления (DRP) и регулярно тестировать его.
- **Безопасность чувствительных данных:** передача и хранение персональных данных требуют строгого соблюдения политик ИБ. Решение — шифрование трафика, минимизация хранения данных, аудит доступа.
